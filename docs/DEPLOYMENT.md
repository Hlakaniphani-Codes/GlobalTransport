# Production deployment

This guide deploys Global Ride Transport to Render and builds the mobile app with Expo EAS. Replace every example domain, email address and identifier with values approved for the client. Do not put passwords, API secrets or database credentials in source control.

## 1. Prepare the repository

1. Push the project to a private GitHub repository.
2. In Render, choose **New > Blueprint**, connect the repository and select `render.yaml`.
3. The blueprint creates PostgreSQL, the API web service and the admin static site. No instance plans are fixed in the blueprint; select plans in the Render dashboard after reviewing current availability and expected use.
4. Wait for Render to create the services and note their generated hostnames.

## 2. Configure Render environment variables

Set the backend values under **global-ride-api > Environment**. Render supplies `PORT` for web services; the application uses port 3000 when run locally.

| Variable | Where to set it | Value |
| --- | --- | --- |
| `NODE_ENV` | Backend service | `production` |
| `PORT` | Render-managed; local backend `.env` | Render's assigned port; locally use `3000` |
| `DATABASE_URL` | Backend service, supplied by the blueprint | Internal connection string from the Render PostgreSQL database |
| `DATABASE_SSL` | Backend service | `false` for Render's internal database connection |
| `DB_POOL_MAX` | Backend service | `10` by default; size from the connection-budget calculation below |
| `DB_POOL_MIN` | Backend service (optional) | `0` by default |
| `DB_IDLE_TIMEOUT_MS` | Backend service (optional) | `30000` by default |
| `DB_CONNECT_TIMEOUT_MS` | Backend service (optional) | `5000` by default |
| `STATEMENT_TIMEOUT_MS` | Backend service (optional) | `15000` by default |
| `IDLE_IN_TRANSACTION_TIMEOUT_MS` | Backend service (optional) | `15000` by default |
| `SLOW_QUERY_MS` | Backend service (optional) | `200` by default; normalized SQL is logged without parameter values |
| `REQUEST_TIMEOUT_MS` | Backend service (optional) | `30000` by default |
| `WORKER_BATCH_SIZE` | Backend service (optional) | `200` jobs per tick by default |
| `NOTIFICATION_RETENTION_DAYS` | Backend service (optional) | `90` days by default |
| `METRICS_TOKEN` | Backend service, generated by the blueprint | Render generates a secret bearer token; required for production startup and used to protect `/metrics` |
| `REDIS_URL` | Backend service (optional) | Set only if shared rate-limit storage is required across multiple API instances |
| `JWT_SECRET` | Backend service, generated by the blueprint | A random value of at least 32 characters; never share or commit it |
| `CORS_ORIGINS` | Backend service | Exact admin origin, for example `https://admin.example.com`; include scheme and omit paths/trailing slash |
| `TRIP_START_WINDOW_MINUTES` | Backend service | `90` |
| `LATE_CANCELLATION_HOURS` | Backend service | `2` |
| `VITE_API_URL` | Admin static site | API origin plus `/api/v1`, for example `https://api.example.com/api/v1` |
| `VITE_SUPPORT_EMAIL` | Admin static site | Monitored support email shown on the account-deletion page |

`CORS_ORIGINS` must match the admin site's exact HTTPS origin. Separate multiple origins with commas. Do not use wildcards. After setting it, redeploy the backend. The static site variables are build-time values; redeploy the admin site after changing them.

### Select instance and database sizes

Choose service and PostgreSQL plans from measured staging capacity and the provider's current plan limits; do not infer capacity from instance counts alone or use provider pricing as a sizing proxy. The production target is 1,000 concurrent users. Before deployment, run the staging scenarios in [LOAD_TESTING.md](./LOAD_TESTING.md) using the intended API instance count, database plan, `DB_POOL_MAX`, worker batch size and rate-limit configuration.

For each API instance, `DB_POOL_MAX` is the maximum number of database connections opened by that instance's pool. Calculate the peak:

```text
peak connections =
  (API instances x DB_POOL_MAX)
  + worker connections
  + migration connections
  + other operational connections
```

Keep peak connections at or below 80% of the selected PostgreSQL plan's connection limit; reserve the remaining 20% for maintenance and operational access. Fill in this table using the actual plan limits and measured worker/operations usage before rollout:

| Selected app plan / instances | Selected PostgreSQL plan | Database connection limit | DB_POOL_MAX | Worker connections | Migration/operations connections | Calculated peak | 80% budget | Within budget? |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| To be measured/selected | To be measured/selected | — | 10 default | To be measured | To be measured | — | — | Pending |

If the connection budget is exceeded, reduce `DB_POOL_MAX` or instance count or select a database plan with a suitable connection limit, then repeat the tests. Do not deploy on an unmeasured estimate. Keep `REDIS_URL` unset when a single-instance in-memory rate-limit store is sufficient; Redis is optional and used only for rate-limit state.

Load-test-only variables (`LOADTEST_ALLOW`, `LOADTEST_DATABASE_URL`, `LOADTEST_PASSWORD`, `LOADTEST_BASE_URL`, `LOADTEST_ENVIRONMENT`, and `LOADTEST_ADMIN_*`) must never be configured on the production service. Set them only in a separate test/staging environment and follow the explicit database/host guards in the load-testing guide.

For local development, `CORS_ORIGINS` may be omitted: the API accepts browser origins from localhost, private IPv4 networks (`10/8`, `172.16/12`, `192.168/16`) and `.local` hostnames. The backend and Vite development server bind to `0.0.0.0` so devices on the same reachable network can connect. A physical phone cannot reach the development computer using `localhost`: use the computer's LAN IP in the mobile API URL. Native mobile requests do not use browser CORS; Expo web requests from the LAN are allowed in development. Keep the development computer's firewall enabled and only share access on a trusted network. These local allowances are disabled in production. On Render, set `CORS_ORIGINS` to the exact admin HTTPS origin(s); do not use `*`. Mobile production builds connect to the public API HTTPS URL and do not require wildcard CORS. Do not use an HTTP URL in a production mobile build.

## 3. Database migrations and first administrator

The backend deploy runs `npm run migrate` as its pre-deploy command before starting. It is safe to run the migration command again; do not manually alter or delete production records to make a deployment succeed. If a migration fails, read the Render service logs, correct the cause, then redeploy. The same command can be run in the API service's Render Shell.

Create the first administrator by opening the Render PostgreSQL database's SQL interface and running the following statement after replacing every placeholder. Use a unique, randomly generated password from a password manager. Do not use the placeholder text as a password.

```sql
INSERT INTO users (
  email,
  password_hash,
  role,
  name,
  surname,
  contact_number,
  is_active
)
VALUES (
  'admin@your-domain.example',
  crypt('<REPLACE_WITH_A_UNIQUE_STRONG_PASSWORD>', gen_salt('bf', 12)),
  'admin',
  '<FIRST_NAME>',
  '<LAST_NAME>',
  '<CONTACT_NUMBER>',
  TRUE
);
```

The schema installs PostgreSQL's `pgcrypto` extension, which provides `crypt` and `gen_salt`. Use the admin site's `/login` page to sign in and immediately confirm access. If the email already exists, do not create a duplicate or reset a production account without authorization; use the approved account recovery process.

The schema no longer creates a default administrator. Removing that seed from the schema does not delete or change an administrator row already present in a database.

## 4. Deploy the admin website

After the API hostname is available:

1. Set `VITE_API_URL` to `https://<API-HOST>/api/v1`.
2. Set `VITE_SUPPORT_EMAIL` to the monitored support address.
3. Add the exact admin site's HTTPS origin to backend `CORS_ORIGINS`.
4. Deploy the API and then redeploy the static site.
5. Open `/health/ready` on the API hostname; it should return `{"status":"ready"}` once PostgreSQL, migrations and the worker are ready. `/health` is a compatibility check for PostgreSQL only. Then visit the admin site, sign in and check the public `/privacy`, `/terms` and `/delete-account` pages.

## 5. Configure Expo EAS

Install Node.js LTS and EAS CLI, then from a Windows PowerShell terminal:

```powershell
cd mobile
npx eas-cli login
npx eas-cli init
```

Create or select the Expo project. Copy its project UUID to `EAS_PROJECT_ID` in the EAS environment. Configure the following values for each EAS environment used by the development, preview and production profiles. The repository deliberately does not embed example URLs or client identifiers in `eas.json`; EAS builds fail before compiling if the required deployment values are missing or still look like placeholders.

| Variable | Where to set it | Value |
| --- | --- | --- |
| `APP_IDENTIFIER` | Each EAS build profile | Client-approved reverse-DNS identifier, such as `com.clientname.globalride`; it must be unique in each app store |
| `EAS_PROJECT_ID` | Expo app configuration environment | UUID returned by `eas init` |
| `EXPO_PUBLIC_API_URL` | Each EAS profile | Deployed HTTPS API origin only, without `/api/v1` |
| `EXPO_PUBLIC_LEGAL_BASE_URL` | Each EAS profile | Deployed public admin-site HTTPS origin |
| `IOS_BUILD_NUMBER` | iOS/local app configuration, if overriding | Positive incrementing build number |
| `ANDROID_VERSION_CODE` | Android/local app configuration, if overriding | Positive integer, incremented for each Play Store release |
| `EXPO_PUBLIC_TRIP_START_WINDOW_MINUTES` | Optional EAS profile setting | Keep aligned with backend `TRIP_START_WINDOW_MINUTES` (normally `90`) |
| `EXPO_PUBLIC_SUPPORT_PHONE` | Optional EAS profile setting | Monitored support number in international format |

`EXPO_PUBLIC_` values are embedded in the app and are not secrets. Never put `JWT_SECRET`, database credentials or other secrets in EAS public variables. Confirm the selected EAS environment is attached to each build profile before building.

Build a preview APK, then create store builds:

```powershell
npx eas-cli build --profile preview --platform android
npx eas-cli build --profile production --platform android
npx eas-cli build --profile production --platform ios
```

Submit only after client-approved branding, legal documents and store information are ready. Apple builds require access to the client's Apple Developer account and signing setup.

The repository's current icon and splash images are Expo starter artwork, not confirmed client-approved assets. The adaptive icon foreground is 512x512 and the app icon has transparency. Replace them with approved artwork before production: app icon 1024x1024 with no transparency, Android adaptive foreground 1024x1024, and approved high-resolution splash artwork.

- [ ] Publish attorney-approved privacy and terms pages at stable HTTPS URLs; signup links use these public pages.

- [ ] Replace all example domains, support contacts and app identifiers.

- [ ] Confirm `CORS_ORIGINS` contains only the production admin origin(s).

- [ ] Obtain client attorney approval for legal drafts and client approval for all artwork.

## 8. Troubleshooting

| Symptom | Check |
| --- | --- |
| API service fails during startup | Review Render logs for missing configuration. Confirm `DATABASE_URL`, a 32-character-or-longer `JWT_SECRET`, a `METRICS_TOKEN`, valid `NODE_ENV`, and a non-empty exact `CORS_ORIGINS` in production. Never paste secret values into support tickets. |
| `/health/ready` returns 503 | Check PostgreSQL availability, database network access, completed migrations, and the worker heartbeat. |
| Browser reports a connection/CORS error | Confirm `VITE_API_URL` is the API hostname plus `/api/v1`, the static site has been rebuilt, and the exact admin HTTPS origin is in `CORS_ORIGINS`. |
| Mobile app cannot connect | Confirm `EXPO_PUBLIC_API_URL` points to the deployed HTTPS API origin without `/api/v1`. For local device testing, `localhost` refers to the device, not the development computer. Rebuild after changing public variables. |
| Admin routes return 404 after refresh | Confirm the static site's `/*` rewrite to `/index.html` is active. |
| Migration fails | Read the database error in Render logs, verify the database is reachable, and deploy again after correcting the issue. Do not drop tables or delete data to bypass a failed migration. |
| EAS reports missing project or identifiers | Set `EAS_PROJECT_ID` from `eas init` and replace the sample `APP_IDENTIFIER` with the client's store identifier. |
| Store build is rejected | Check signing credentials, build numbers, approved artwork, privacy/data-safety disclosures, deletion URL and reviewer instructions in the relevant store console. |
